# Цифровая визитка

GraphQL API, которое отдаёт профиль, навыки, опыт и проекты. Интерфейс для запросов — Apollo Sandbox на `/graphql`.

Стек: TypeScript, Node.js, NestJS, Prisma, GraphQL, PostgreSQL, Docker.

## Запуск с нуля

Нужны Docker и Docker Compose.

```bash
docker compose up --build
```

При старте контейнер сам дожидается PostgreSQL, применяет миграции и заполняет базу данными из `src/profile/profile.content.ts`. Повторный запуск не дублирует строки: перед записью профиль пересобирается в одной транзакции.

- Apollo Sandbox: http://localhost:3000/graphql
- Проверка, что процесс жив: http://localhost:3000/health

Пример запроса:

```graphql
query {
  profile {
    name
    description
    skills {
      name
    }
    experience {
      company
      position
    }
    projects {
      name
    }
  }
}
```

Postgres опубликован на порту `5433`, чтобы не пересекаться с локальным сервером на `5432`. Учётные данные в `docker-compose.yml` только для локального запуска.

## Локальная разработка

```bash
docker compose up -d db
cp .env.example .env
npm install
npx prisma generate
npm run start:dev
```

Полезные команды:

```bash
npm test
npm run test:e2e
npm run build
```

`test:e2e` компилирует приложение и гоняет запросы к GraphQL. Ему нужна база из `DATABASE_URL`: тест сам накатывает миграции и заново записывает профиль.

## Архитектура

Один модуль предметной области — визитка. Запись API нет: карточку не редактируют через GraphQL, источник данных — код.

```text
Apollo Sandbox
  -> ProfileResolver          GraphQL, без знания SQL
  -> ProfileService           сценарий «отдать профиль» и группировка строк
  -> ProfileRepository        запросы Prisma
  -> PostgreSQL
```

Слои:

- `src/profile/profile.resolver.ts` — схема и резолверы. Корневой запрос возвращает только `id`, имя и описание.
- `src/profile/profile.service.ts` — сценарий чтения. Если профиля нет, это ошибка, а не пустой ответ.
- `src/profile/profile.repository.ts` — единственное место с запросами к таблицам.
- `src/profile/profile.mapper.ts` — граница между строками Prisma и GraphQL-типами. Период работы здесь считается из дат, в базе он не хранится.
- `src/profile/profile.content.ts` — текст визитки. Чтобы поменять имя, опыт или проекты, правится этот файл. Сейчас там публичное имя с GitHub и самостоятельные проекты.

GraphQL-типы описаны кодом (`@ObjectType`), а не отдельным SDL. TypeScript остаётся источником схемы, Sandbox получает её через introspection.

## Вложенные данные

Связи не подгружаются через `include` в корневом запросе. Иначе база читала бы навыки, опыт и проекты даже тогда, когда клиент спросил только имя.

У каждого вложенного поля свой резолвер. Резолвер берёт DataLoader из контекста запроса. Loader собирает идентификаторы профилей и делает один `WHERE profileId IN (...)` на связь. Достижения приезжают вместе с опытом (`include` только внутри этого запроса), отдельного запроса на каждое достижение нет.

Для одного профиля полный запрос — это один `SELECT` профиля и ещё по одному на каждую выбранную связь. Невыбранное поле не порождает запрос. Loader создаётся заново на каждый HTTP-запрос, поэтому кеш DataLoader не переживает запрос. Сервисы при этом остаются обычными singleton: request-scope на весь модуль не включался.

## База

PostgreSQL. Модель намеренно уже, чем ответ GraphQL:

- `Profile` один, со стабильным `slug`.
- Ссылки, навыки и проекты — отдельные таблицы с порядком `sortOrder`.
- Опыт хранит компанию, должность и даты. Текст периода собирается в `formatPeriod`.
- Достижения — строки у опыта, а не массив в колонке: их можно упорядочить и не тащить формат массива конкретной СУБД.

Миграции лежат в `prisma/migrations` и применяются командой `prisma migrate deploy` из процесса приложения до `listen`. Отдельный ручной шаг не нужен.

Сид идемпотентный. Транзакция берёт `pg_advisory_xact_lock`, удаляет профиль (связи уходят каскадом) и создаёт его заново из `profile.content.ts`. Два одновременных старта не перемешают данные. Ручные правки в базе при следующем старте затрутся: для этой визитки код — источник правды.

Prisma ORM 7. Клиент генерируется в `src/generated` и не коммитится. Подключение к Postgres идёт через драйвер `pg` и `@prisma/adapter-pg`, строка подключения для CLI — в `prisma.config.ts`.

## Почему так

- Read-only API. Мутации без аутентификации для публичной визитки не нужны.
- Apollo Sandbox включён и в production, introspection тоже. Это и есть интерфейс задания, данные публичные. В NestJS 14 встроенный playground убран, поэтому landing page задан явно через `ApolloServerPluginLandingPageLocalDefault`.
- `/health` не входит в визитку. Он нужен, чтобы Docker понял, что миграции и сид уже прошли и процесс слушает порт.
- Postgres в Compose, а не SQLite. Так проверяется тот же путь, что и у ревьюера: пустой volume, миграции, сид, затем запрос.

## Тесты

Юнит-тесты закрывают формат периода и группировку строк по профилю: это места, где легко получить чужой порядок или сдвинуть дату из-за часового пояса. Сквозной тест поднимает приложение и выполняет запрос из задания плюс вложенные ссылки, период и достижения.

## Деплой

Образ самодостаточный: внутри есть Prisma CLI, схема и миграции. На Render или Railway достаточно веб-сервиса из этого Dockerfile и managed Postgres. В переменные окружения сервиса нужно передать `DATABASE_URL` и `PORT`. После старта Sandbox будет на `/graphql`.
